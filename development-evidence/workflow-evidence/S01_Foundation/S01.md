## Goal and scope

Establish the foundation used by later slices: centralized SQLite persistence, a shared Domain Rules gateway, public service interfaces, an event publish/consume foundation, and automated tests.

## Acceptance criteria and basic checks

Plan acceptance criteria:

- [x] The application starts and its layers have the documented responsibilities (Flask routes in `app.py`; business modules; `Data_Access`).
- [x] Persistent data is accessed through the Data Access Layer (`Data_Access.database`; event SQL only in `Data_Access.event_store`). Existing business modules obtain connections from Data_Access and run their own SQL; moving it into Data_Access functions was not part of this round.
- [x] A state-changing operation can be rejected by Domain Rules without committing its changes (for example an invalid status transition commits neither the change nor an event).
- [x] Modules communicate through service interfaces and events (`Events.publish_event`, `register_handler`, `process_pending_events`).
- [x] Event processing records identifiers and supports the retry/failure policy (unique `event_id`, `processed_events`, attempts, `last_error`, failed status) — with **PROVISIONAL** retry values pending G-12.
- [x] The UI shell supports desktop and mobile layouts (viewport meta tag, fluid layout). Not verified against a browser list (G-13).

Foundation checks:

- [x] `init_db()` creates the users, tasks, study_sessions, reminders, availability, staged_imports, sync_logs, events and processed_events tables.
- [x] User-owned tables carry `user_id` foreign keys; foreign-key enforcement is on.
- [x] Database initialization is idempotent and migrates older databases, including the tasks table rebuild (nullable deadline, `incomplete`/`completed` statuses; data and composite foreign keys preserved).
- [x] `Domain_Rules` exposes `DomainRuleError` and validators for task title, deadline (required and optional), status transitions, time ranges, weekdays, reminder values, course, email, password, event type and event payload. Authentication uses the email and password validators.
- [x] `events` has unique `event_id`, `event_type`, `user_id`, JSON `payload`, `status` (pending/processed/failed), `attempts`, `last_error`, `created_at`, `processed_at` (plus `last_attempt_at`, added to support the retry interval). `processed_events` has `UNIQUE(event_id, consumer)`.
- [x] `Task_Management` publishes `task.completion_changed` in the same transaction as a completion-status change. No consumers from other slices are registered.

## Remaining limitations and follow-up work

- G-01 technology choices were made by the AI and are not group-approved.
- Events are not processed automatically: no scheduler or background worker exists, so `process_pending_events` must be called by something (G-01, G-15). Events with no registered handler stay pending.
- Delivery is at-least-once with duplicate suppression per (event, consumer); a crash between a handler finishing and its record being written could repeat that handler, so handlers should tolerate a repeat. Concurrent processors are not coordinated.
- Event processing is system-wide (not user-scoped); read access to events is user-scoped. Operator access to failed events is open (OI-08).
- Retry interval and maximum attempts are provisional (G-12). `last_attempt_at` was added beyond the listed event fields to support the interval.
- Out-of-slice code exists early: `Schedule` (S07), `Reminder` (S09), `External_Integration` (S06) and `Priority` (S05) services. They belong to later slices and are not accepted work.
- `Events` is a public foundation module requested for S01; AGENTS.md says new modules need human approval, so the team should confirm it.
- Backup and recovery (S12) are not started.
